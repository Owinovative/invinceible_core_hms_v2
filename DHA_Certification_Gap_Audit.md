# DHA HIE Certification Gap Audit

Date: 2026-07-14

Scope: current `codex/dha-hie-core-contracts` code, `DHA_HIE_Complete_Reference.md`,
`DHA_Implementation_Report.md`, and the current official DHA HIE documentation.
Only unresolved certification blockers are listed.

## Critical

| Gap | Why it exists and impact | Affected evidence | Required implementation |
| --- | --- | --- | --- |
| Automatic SHA claim submission is a guaranteed non-compliant dead-letter path | `onShaClaimSubmitted` builds a FHIR `Claim` bundle and queues `SUBMIT_CLAIM`; the queue worker rejects every `CLAIM_SUBMISSION` whose resource type is not `DHA_ECLAIMS_COMMAND`. A normal UI/manual submission therefore cannot complete DHA eClaims, despite being exposed to users. This blocks claims certification. | `backend/src/integration/dha/dha.service.ts:279`, `:421`, `:650`; `backend/src/sha-claims/sha-claims.controller.ts:100`; `frontend/services/dha-service.ts:191` | Replace the FHIR-claim trigger with a persisted DHA visit/authorization/intervention/line/preview/submit state machine. Store DHA IDs and transitions per SHA claim, route UI actions through it, and remove the legacy submit endpoint until migrated. |
| No durable multipart/file workflow | DHA requires multipart attachments, preauth creation, EMT, uploads, and OTP-whitelist requests. The HTTP client can transmit `FormData`, but there is no attachment model, encrypted file persistence, upload controller, queue payload reference, multipart adapter method, or workflow/UI. The encryption key is only a startup gate. This blocks preauth, EMT, attachments, uploads, and whitelist certification. | `backend/src/integration/http/integration-http.client.ts`; `backend/src/integration/dha/eclaims-contract.ts`; `backend/src/config/env.validation.ts:98`; no DHA attachment model in `backend/prisma/schema.prisma` | Add encrypted-at-rest attachment records, file-size/type validation, malware scanning policy, durable file references, queue reconstruction of `FormData`, and endpoint-specific multipart DTOs/workflows. Do not store raw files in queue JSON. |
| SHR publication has no registered outbound handler or documented DHA transport | `ShrPublisher` queues `PUBLISH_SHR_BUNDLE`, but no worker registers that operation. The current publisher cannot deliver any SHR bundle. The official current documentation also exposes clinical document/FHIR routes, while this path has no confirmed endpoint/profile mapping. This blocks SHR certification. | `backend/src/shr/shr-publisher.service.ts:16`; worker registrations only in `backend/src/integration/dha/dha.service.ts:79-94`; `backend/src/shr/shr-webhook.controller.ts` | Obtain DHA-approved SHR/FHIR profile and callback contract; implement a registered queue handler, endpoint-specific payload mapping, acknowledgement/reconciliation, retry/DLQ handling, and UAT conformance tests. |

## High

| Gap | Why it exists and impact | Affected evidence | Required implementation |
| --- | --- | --- | --- |
| Live FHIR placeholder routes are not official DHA contract routes | Encounter, bundle/record exchange, referral, consent, and audit methods post to relative `Encounter`, `Bundle`, `ServiceRequest`, `Consent`, and `AuditEvent` paths. These are not the current published DHA API contracts. They are reachable through controllers and queue handlers, so calls will be rejected or sent to an unsupported route. | `backend/src/integration/dha/adapters/dha-http.client.ts:300-365`; `backend/src/integration/dha/dha.controller.ts:106-133`; `backend/src/integration/dha/dha.service.ts:537-590` | Disable these routes in sandbox/production until DHA supplies the governing profile; then map to current documented clinical endpoints such as `/clinical/fhir/bundle` or `/clinical/service-requests` and validate the approved schemas. |
| Parallel legacy DHA integrations bypass the canonical DHA adapter | `IntegrationsModule` enables a second set of registry and terminology clients with retired `afyalink.dha.go.ke` defaults and FHIR-style CR/FR/PR/terminology paths. They do not share canonical DHA configuration, facility headers, queue semantics, or current endpoint contracts. This creates conflicting traffic and invalid registry/terminology behavior. | `backend/src/integrations/integrations.module.ts`; `backend/src/integrations/client-registry/client-registry.service.ts:44-159`; `facility-registry.service.ts:24`; `practitioner-registry.service.ts:24`; `terminology/terminology.service.ts:26-73` | Remove, retire, or refactor these services to delegate to `DhaClientPort` and `TerminologyGatewayService`; delete stale production defaults and add tests proving there is one DHA transport path. |
| Current official DHA clinical API surface is absent | The official June 2026 changelog lists clinical FHIR bundle, documents, encounters, questionnaires, medication requests/dispenses, ICD-11/LOINC, and service-request APIs. The repository has local SHR/FHIR models but no verified DHA client/controller/workflow mappings for these current endpoints. This blocks clinical exchange, referrals, document and questionnaire certification where in scope. | No `clinical/*` adapter operations in `backend/src/integration/dha/eclaims-contract.ts`; placeholder FHIR methods above | Confirm licensed integration scope with DHA, then add endpoint-specific clients, DTOs, validations, persistence, queue handlers, UI flows, and UAT tests for every required clinical scenario. |
| eClaims command endpoint is a generic privileged pass-through, not a domain workflow | `POST /integrations/dha/eclaims/:operation` accepts arbitrary object payload/query plus a caller-selected operation. It does not bind commands to local SHA claims, invoices, consultations, consent/visit IDs, provider identity, tariff results, or UI state. It cannot enforce transition order or reconstruct a compliant patient journey. | `backend/src/integration/dha/dha.controller.ts:137-158`; `dto/dha-requests.dto.ts`; `dha.service.ts:205-260` | Replace generic exposure with domain-specific claim/preauth/prescription/emergency workflow commands backed by persisted DHA identifiers and state-transition guards. Keep the contract layer internal. |
| Current DHA contract drift is not controlled | The official changelog currently documents contract changes that conflict with the local contract: authorization lookup requirements, required `sub_benefit_code` for benefit interventions, additional clinical APIs, multipart variants, and specialised preauth schemas. There is no OpenAPI snapshot, contract-test pipeline, or version pin. | `backend/src/integration/dha/eclaims-contract.ts`; official [DHA changelog](https://hie-docs.dha.go.ke/changelog) | Vendor/pin a DHA OpenAPI release, generate or assert endpoint schemas, run contract tests in CI, and define a documented change-management process before UAT. |
| No production-grade callback assurance | Callback verification is a locally invented bearer shared-secret mechanism. The existing report correctly notes DHA has not supplied certificate/trust/signature/JWT rules; therefore callback authenticity is not proven for certification. | `backend/src/integration/dha/dha.controller.ts`; `backend/src/shr/shr-webhook.controller.ts`; `DHA_Implementation_Report.md` | Obtain DHA callback security specification and UAT credentials; implement the exact mTLS/JWS/JWT or signed-header verification, replay protection, timestamp validation, key rotation, and negative tests. |

## Medium

| Gap | Why it exists and impact | Affected evidence | Required implementation |
| --- | --- | --- | --- |
| Consent-token restoration can select the wrong authorization | Queue execution loads the latest active patient consent, optionally scoped only by consultation. The persisted command does not carry a durable authorization/visit identifier, so retries may hydrate a newer consent token than the token used to create the DHA claim. This risks cross-visit claim mutation and audit failure. | `backend/src/integration/dha/dha.service.ts:219-227`, `:604-627`; `backend/prisma/schema.prisma` `ConsentAuthorization` model | Persist the DHA authorization/visit reference and a local authorization ID on each workflow record; load that exact record on retry and reject expired/revoked tokens deterministically. |
| Result mapping can mark non-success DHA statuses complete | `toResult` only treats a small fixed set of statuses as negative; the worker only marks `REJECTED` as failed. A successful HTTP response with a DHA failure/pending/invalid status can be recorded `COMPLETED`, losing required remediation. | `backend/src/integration/dha/adapters/dha-http.client.ts:213-238`; `backend/src/integration/dha/dha.service.ts:670-705` | Define endpoint-specific response/status schemas and a terminal-state matrix. Mark only documented accepted terminal states complete; retain pending/retryable states and dead-letter documented permanent failures. |
| UI does not implement DHA patient journeys | The frontend exposes eligibility, basic verification, consent OTP and the legacy `submit-to-dha` action. It contains no user flow for visit creation, benefit/intervention selection, provider identity, line/diagnosis editing, preview/submit/discharge, preauth variants, files, emergency/EMT, prescriptions, or callback outcome remediation. | `frontend/services/dha-service.ts`; `frontend/services/consent.service.ts`; no frontend eClaims/preauth service or route | Build role-scoped clinical/billing workflows that call the domain APIs, display DHA validation errors/statuses, preserve drafts, and prohibit out-of-order submissions. |
| Existing DHA tests are not certification evidence and cannot run | `backend/node_modules/.bin/nest` and `jest` are absent. Existing tests still cover FHIR claim submission assumptions that contradict the worker’s fail-closed path. No DHA sandbox UAT, security, multipart, workflow, callback, or contract test evidence exists. | `backend/src/integration/dha/dha.service.spec.ts`; `DHA_Implementation_Report.md`; local dependency check | Restore reproducible dependency installation, repair obsolete tests, add unit/integration/contract/UAT suites, and archive passing execution evidence per DHA scenario. |
| Environment configuration does not establish DHA operational readiness | Required base credentials/facility/secret/key are validated, but there is no configured certificate/trust-store, callback issuer/key configuration, UAT tenant test-data mapping, operator runbook, or go-live evidence. | `backend/src/config/env.validation.ts`; `backend/.env.example`; `backend/src/integration/integration-config.service.ts` | Add DHA-provisioned mTLS/signature configuration after specification receipt, secret rotation/runbook references, environment segregation, UAT scenario variables, and release gates. |

## Certification Decision

**Not eligible for DHA UAT certification, production enablement, or go-live.**

The Critical items must be resolved first. High items then require DHA contract confirmation and UAT evidence; external DHA-issued credentials, certificate/signature rules, test data, and formal acceptance remain mandatory regardless of code completion.
